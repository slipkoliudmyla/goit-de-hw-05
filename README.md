# Apache Kafka — моніторинг сенсорів

Домашнє завдання 5 курсу Data Engineering. Один процес `producer.py` представляє один сенсор зі сталим ID. Два процеси передають випадкові показники в Kafka, окремий споживач фільтрує їх, а інший читає алерти.

## Вимоги

- Python 3.12 і `pip install -r requirements.txt`.
- Запущений Apache Kafka. Перевірено з Kafka 3.9.1 у KRaft-режимі на `127.0.0.1:19092`.
- Локальна інструкція запуску брокера: [LOCAL_KAFKA.md](LOCAL_KAFKA.md).

## Запуск

Виконувати команди з каталогу проєкту. Кожен довготривалий процес запускається в окремому терміналі.

```sh
python create_topics.py
python filter_sensors.py
python consume_alerts.py
python producer.py --sensor-id sensor-1
python producer.py --sensor-id sensor-2
```

Спочатку запустіть фільтр і читач алертів, потім два сенсори. Ctrl+C завершує кожен процес. Для обмеженого запуску: `python producer.py --sensor-id sensor-1 --count 30 --interval 1 --seed 5`. `--seed` потрібен лише для повторюваної перевірки; генерація залишається псевдовипадковою.

Налаштування задаються змінними середовища:

```sh
export KAFKA_BOOTSTRAP_SERVERS=127.0.0.1:19092
export KAFKA_TOPIC_PREFIX=slipkoliudmyla
```

За замовчуванням створюються `slipkoliudmyla_building_sensors`, `slipkoliudmyla_temperature_alerts`, `slipkoliudmyla_humidity_alerts`: по 2 партиції, replication factor 1. Це навчальний брокер без відмовостійкості між серверами; він слухає лише loopback. Код не містить облікових даних.

## Правила

- Температура генерується в межах 25–45 °C; алерт — строго `> 40`.
- Вологість генерується в межах 15–85 %; алерт — строго `< 20` або `> 80`.
- Температура 40 і вологість 20 або 80 не створюють відповідного алерту.
- Один запис може створити два алерти. У них зберігаються `id`, `timestamp`, `temperature`, `humidity`, додаються `alert_type` та `message`.
- `send(...).get()` очікує підтвердження Kafka; повідомлення `SENT` містить справжні partition/offset.
- Фільтр зберігає consumer offset після успішного надсилання всіх алертів. Після аварії можливе повторне опрацювання, тому це не гарантія exactly once.
- Повторний запуск із тією самою consumer group продовжує читання зі збереженого offset. Для перевірки від початку використайте нове `--group`.

## Структура

`configs.py` — адреса брокера і назви топіків; `create_topics.py` — створення та список; `producer.py` — один сенсор; `filter_sensors.py` — перевірка порогів; `consume_alerts.py` — читання двох вихідних топіків. У `evidence/` розміщені звіт, скриншоти й фактичні журнали перевірки.

Скриншоти показують браузерний переглядач реального stdout Python-процесів, а не знімки термінала. Значення, PID, partition та offset взяті з виконання; сирі журнали доступні для звірки.
